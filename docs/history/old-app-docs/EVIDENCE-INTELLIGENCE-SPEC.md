## Evidence Intelligence Batch 1 (2026-08-26) — IMPLEMENTED

**Scope:** extraction + provenance + cross-document checking only, as a single stage-independent evidence ledger. Nothing else — no Stage 1/2/3 wiring (see "What Batch 1 deliberately does NOT do" below).

**Where it lives:** a new file, `evidence.js` (loaded in `index.html` alongside `geometry.js`/`drawing.js`, before `app.js` — same pattern, same "single source of truth, stage-independent" spirit as `geometry.js`). It reads project evidence-file text and produces one project-level record, `p.evidenceRecords`, reusing the existing `p.evidence` file-metadata array (see "Backward compatibility" below) rather than creating a second parallel upload store.

**Honesty about what actually reads a file:** this prototype has never read uploaded-file *content* — `app.js`'s `addEvidenceFiles()` has only ever stored name/size/type metadata. Batch 1 adds genuinely-working extraction for the one class of file a browser can read without any new library or backend: plain text (`.txt`/`.md`/`.csv`/`.log`/`.json`, or a `text/*`/`application/json` MIME type), via the standard `File.text()` API — see `isTextReadableFile()`. **Binary formats (PDF, Word, images, scanned documents) are not parsed** — there is no OCR/PDF-text-extraction library in this project, and Batch 1 does not add one. For those, `extractedText` stays `null` and `extractionStatus` records why (`'not_extractable_in_prototype'`), rather than fabricating extracted content. This is the main productionisation gap before Batch 2 can extend to typical real-world uploads (PDF/Word) — see "Governance decision required before Batch 2" below.

**Evidence record schema** (`createEvidenceRecord()`): `evidence_id, project_id, source_file, source_document_type, source_document_type_confidence, source_page_or_section, subject, extracted_value, unit, evidence_status, confidence, extraction_note, corroborates[], conflicts_with[], created_at, superseded_by`.

**Evidence status** (`EVIDENCE_STATUS`): the required minimum five — `CONFIRMED_BY_DOCUMENT`, `ASSUMED_IN_DOCUMENT`, `PROVISIONAL`, `CONFLICTING_EVIDENCE`, `NOT_YET_KNOWN` — plus one addition, `DOCUMENT_INTERNAL_INCONSISTENCY`, for a document contradicting *itself* (e.g. two different figures for the same subject in one document, or inconsistent project-description wording), which is a distinct case from a *cross*-document conflict and would otherwise have no honest status to sit under.

**Document type classification** (`classifyDocumentType()`): transparent keyword scoring across the broad taxonomy in the brief (`DOCUMENT_TYPES`) — every match is inspectable via `matched_terms`; a weak or tied signal is `'other_project_evidence'` at `'low'` confidence rather than a confident guess. Not a black-box classifier.

**Extraction rule table** (`FACT_RULES`): ~24 generic, real-world-phrasing regex rules (not fixed strings copied from one fixture) covering the categories in the brief — ground conditions, bearing pressure, slab thickness/reinforcement, contamination/asbestos/groundwater/gas testing, footprint dimensions, foundation-pad count, provisional sums, assumptions and exclusions. Status per match comes from local sentence context (`classifyStatusFromContext()`): "provisional" language → `PROVISIONAL`; "assum-"/"exclud-"/"no allowance" language → `ASSUMED_IN_DOCUMENT` (an exclusion is explicitly **not** `CONFIRMED_BY_DOCUMENT` — see the brief's own instruction not to treat an exclusion as a site fact); otherwise → `CONFIRMED_BY_DOCUMENT`. A section-heading guard skips a match that is itself just a capitalised heading restating a keyword (not a stated fact).

**Provenance** (`buildLineProvenanceIndex()`/`provenanceAt()`): tracks the most recently seen section heading and/or an explicit `(page N)` marker line-by-line, and attributes each extracted fact to wherever its match starts — real page/section provenance, not a constant placeholder, whenever the source text contains that structure; `'not identified'` otherwise (never fabricated).

**Cross-document checking** (`crossCheckEvidence()`): groups all records for a project by `subject`. Two records for the same subject from **different** source files that are numerically/keyword-equivalent → linked via `corroborates[]` on both, statuses untouched. Two that genuinely disagree → linked via `conflicts_with[]` on both, **both** flipped to `CONFLICTING_EVIDENCE` — neither source is silently preferred, and both keep their own `extracted_value`/provenance. Two records for the same subject from the **same** file with a genuinely different numeric value → `DOCUMENT_INTERNAL_INCONSISTENCY` instead (the same-document case). Where a comparison can't be made safely (different units, non-numeric free text that merely differs in wording) → **no link and no status change** — Batch 1 never invents a corroboration or conflict it can't actually support.

**Validation case (Job L two-document trial):** reconstructed as two test-fixture `.txt` files (not the original documents — the prototype cannot read PDFs; see "Honesty" above) containing the facts already supplied for this trial, run through the real upload path (an actual browser `File.text()` read, not a hand-fed string) and the real extraction/cross-check engine. Results — see this batch's task report for the full ledger — correctly produced: document types (`site_investigation_geotechnical`, `groundworks_quotation`, both `high` confidence); a genuine cross-document corroboration (200 mm slab / two-layer A393 mesh, in both documents, both source records preserved); a genuine cross-document conflict (100 kN/m² recommended vs. 150 kN/m² assumed allowable bearing pressure, both preserved as `CONFLICTING_EVIDENCE`); a genuine same-document internal inconsistency (two different made-ground-depth figures in one report); a flagged inconsistent project-description ("industrial" vs. a leftover "proposed dwelling" reference in the same report, not auto-corrected); two provisional sums ([price redacted] drainage, [price redacted] service duct) correctly kept `PROVISIONAL`; and assumptions/exclusions (existing drainage, underground services, existing-concrete breakout, contaminated-ground disposal) all correctly kept out of `CONFIRMED_BY_DOCUMENT`.

**Internal review surface:** `route('evidenceLedger', projectId)` in `app.js` — reachable via a small, explicitly-labelled "🔧 Internal/dev: view extracted evidence ledger" link on the project workspace's "Project evidence" card. Shows Document → Document type/confidence; then Document → Subject → Extracted value → Status → Confidence → Page/section → Corroboration/conflict, plus the full raw JSON ledger for exact inspection. Clearly banner-labelled "INTERNAL / DEVELOPMENT REVIEW ONLY — NOT SHOWN TO CUSTOMERS" — **this must be gated behind a real internal/admin-only view before production**, not left reachable from the customer-facing project workspace as it is in this prototype batch (flagged below as a governance/productionisation item, not resolved by this batch).

**What Batch 1 deliberately does NOT do** (per the brief's "NO LIVE WORKFLOW CHANGES"): does not pre-populate or skip any Stage 1 question; does not show a "confirm/correct" prompt; does not change a customer's typed answer; does not create a Stage 2 risk card or disclose a Stage 2 finding; does not create a Stage 3 action; does not alter a report. `p.evidenceRecords` is written to the project object and persisted via the existing `save()`, but nothing in `app.js` currently reads it back into any Stage 1/2/3 customer-facing output — only `evidenceLedgerPage()` (the internal review route) reads it.

**Backward compatibility:** existing `p.evidence` entries (from before this batch) have no `extractedText`/`documentType` fields at all — `buildProjectEvidenceLedger()` simply skips any entry without `extractedText` (nothing to extract, nothing faked), and `evidenceLedgerPage()` renders `'—'` for its missing document-type columns. No existing project's `p.evidence` array is rewritten, reordered or deleted. Verified: a fabricated pre-Batch-1-shaped project (one old-style PDF evidence entry, no `evidenceRecords` field at all) loads its workspace and its evidence-ledger page without error.

**Governance decision required before Batch 2** (reported, not decided here): (1) whether/how to add real PDF/Word text extraction (a client-side library, or a future server-side step) — most real customer uploads are PDFs, so Batch 1's plain-text-only extraction is a validation proof, not yet coverage of typical real uploads; (2) the internal evidence-ledger review route must be access-gated before any production exposure — it is a plain, unauthenticated app route in this batch, reachable by anyone signed in; (3) whether/how a later batch is allowed to feed a corroborated/conflicting fact back into Stage 1/2/3 customer-facing behaviour is explicitly **not** decided by this batch and needs its own one-at-a-time governance review, consistent with `MASTER-SPEC.md` § "Question, Evidence & Rule Development governance".

## Evidence Intelligence Batch 1B (2026-08-26) — IMPLEMENTED: real PDF + DOCX extraction

**Scope:** answers Batch 1's governance item (1) above — real, working text extraction from genuine PDF and DOCX files, feeding the exact same pipeline (same schema, same status vocabulary, same corroboration/conflict engine, same internal review route) as Batch 1. No second extraction/intelligence system was created; no Stage 1/2/3 behaviour changed.

**PDF extraction:** `extractTextFromPdf()` (`evidence.js`) uses **pdf.js 3.11.174** (Apache-2.0), vendored locally at `assets/vendor/pdfjs/pdf.min.js` + `pdf.worker.min.js` (referenced in `index.html`) rather than fetched from a live CDN — same-origin, so no CSP change was needed, and the exact version is pinned. Extracts real per-page text via pdf.js's passive `getTextContent()` API (no annotations/forms/embedded-JS execution is ever invoked). Real page boundaries are preserved as literal `(page N)` markers between pages — these are pdf.js's own real page indices, reusing the exact page-marker pattern `buildLineProvenanceIndex()` already recognised in Batch 1, so no provenance-model change was needed for PDF. An image-only/scanned PDF (zero pages with any extractable text) is marked `OCR_REQUIRED` and produces **zero** evidence records — OCR was not attempted, per instruction.

**DOCX extraction:** `extractTextFromDocx()` (`evidence.js`) uses a from-scratch minimal ZIP central-directory reader (`readZipEntryText()`) plus the browser's native `DecompressionStream('deflate-raw')` for DEFLATE-compressed entries — no new library. `word/document.xml` is parsed via the browser's native `DOMParser` (inert XML parsing only — no macro/embedded-object execution, no external reference ever fetched or followed) and walked for `<w:p>` paragraphs and `<w:t>` runs (`wordXmlToPlainText()`); table-cell paragraphs are ordinary `<w:p>` elements nested inside `<w:tbl>`, so `getElementsByTagName('w:p')`'s descendant search already includes table text with no separate code path. Paragraphs styled `Heading*`/`Title` in the source `<w:pStyle>` are marked with a `HEADING_SENTINEL` (a U+0001-control-character-delimited marker, never legitimately present in real document text, so it can never collide with real content) that `buildLineProvenanceIndex()` was extended to recognise as ground-truth section provenance — a small, targeted extension of the *same* provenance function, not a parallel one. DOCX has no native page concept, so no page number is ever invented, per instruction.

**Single dispatcher:** `extractEvidenceText()` is the one new entry point `app.js`'s `addEvidenceFiles()` calls for every uploaded file — it decides plain-text vs. PDF vs. DOCX vs. unsupported, so there is exactly one extraction reasoning path regardless of format, never a second system.

**Extraction status vocabulary** (`EXTRACTION_STATUS`, one shared vocabulary across every format): `EXTRACTED`, `PARTIAL` (some but not all content — e.g. a PDF with some scanned pages, or a truncated document), `OCR_REQUIRED`, `UNSUPPORTED` (no extractor exists for this file type), `EXTRACTION_FAILED` (recognised type but parsing threw / malformed / over the size limit). Batch 1's two earlier ad-hoc values (`'text_read'`, `'not_extractable_in_prototype'`) are superseded by `EXTRACTED`/`UNSUPPORTED` respectively — a deliberate, documented rename, not a silent behaviour change (nothing else in the codebase branched on the old literal strings).

**Limits (reported, not silent):** 25 MB per file, 200 PDF pages, 2 MB of extracted text per document — each produces a clear note (never a silent truncation) when hit.

**Security:** no embedded document content is ever executed (pdf.js text-layer extraction and DOMParser XML parsing are both passive/inert by construction — this is not a configuration this app disables, it is what these APIs do); no embedded link/reference is ever followed; every extraction path is wrapped so a malformed/corrupted file produces `EXTRACTION_FAILED`, never a crash — verified with a deliberately corrupted fake `.pdf` and fake `.docx`.

**Real Job L validation:** two genuinely real, pre-existing Job L files were located and used (not reconstructed) — a real text-based PDF (`[client file name redacted]`, an intrusive concrete-crush/condition investigation, genuinely confirming "Job L/College Road/Job L site") and a real scanned PDF from the same trial (`Q22-06-22 Intrusive SI Job L Water Site -.pdf`), which correctly produced `OCR_REQUIRED` with zero records — a genuine, not fabricated, scanned-document test case. A real DOCX (`Job L building document.docx`) was also located and genuinely extracted. The specific figures originally described for the "groundworks quotation" (51 m × 21 m, 29 pads, [price redacted]/[price redacted] provisional sums) were **not found in a matching real file on this machine** after a thorough search — see this batch's task report for exactly what was searched. To still prove the real-PDF/DOCX pipeline reproduces Batch 1's validated corroboration/conflict/assumption/provisional results end-to-end, a genuine real PDF (via jsPDF, already used elsewhere in this app for customer reports) and a genuine real DOCX (via a hand-built ZIP writer, Node's built-in `zlib` only) were generated containing that content, and uploaded through the real browser upload path. Result: identical corroborations (200 mm slab / two-layer A393 mesh, now proven **across two different real binary formats**, not two `.txt` files), identical cross-document conflict (100 kN/m² vs. 150 kN/m² bearing pressure, both preserved), identical assumptions/exclusions/provisional sums — full detail in the task report.

## Evidence Intelligence Batch 2 (2026-08-26) — IMPLEMENTED: Stage 1 evidence assistance

**Scope:** connects the existing ledger (Batch 1/1B) to the EXISTING Stage 1 customer journey — assistance only, never automation. No Stage 2/3 behaviour, question, report, price, map or drawing changed; no Stage 1 question deleted, reordered or reworded; every existing question remains **LOCKED-EXISTING**.

**Where it lives:** appended to `evidence.js` (same file, no second system) — `STAGE1_EVIDENCE_MAP`, `STAGE1_CONTEXT_MAP`, `isProposableEvidence()`, `assessStage1QuestionEvidence()`, `applyStage1EvidenceConfirm()`, `recordStage1EvidenceCorrection()`. `app.js`'s `stage1()` renders the (optional) evidence-assist banner above the unchanged question input; `saveStage1()` gained one small addition (records a correction when the customer's own typed answer diverges from a live proposal — never blocks the save); two new handlers, `confirmStage1Evidence()`/`correctStage1Evidence()`.

**Required states** (`STAGE1_ASSIST_STATUS`): `UNANSWERED` (no answer, no usable evidence), `NEEDS_CUSTOMER_CONFIRMATION` (no answer yet, a `CONFIRMED_BY_DOCUMENT`, non-low-confidence record exists — shown with Confirm/Correct, never auto-applied), `ANSWERED_BY_EVIDENCE` (the customer has explicitly confirmed a proposal), `CONFLICTING_EVIDENCE` (either a cross-document disagreement on the mapped subject, or new evidence disagreeing with an answer the customer already gave — never auto-resolved, both sides always retained).

**Mapping layer** (`STAGE1_EVIDENCE_MAP`/`STAGE1_CONTEXT_MAP`): explicit, inspectable EVIDENCE SUBJECT → STAGE 1 QUESTION table, not raw keyword matching. Every one of the 17 Stage 1 questions was individually evaluated against the subjects Batch 1/1B's `FACT_RULES` actually produce; only three clear that "is it specific enough to answer this exact question, in this exact answer format?" bar for a full Confirm/Correct proposal (`use`, `width`, `length`), and one subject pair is mapped as **context-only** (`services`, backed by `underground_services_assumption`/`existing_drainage_assumption` — both `ASSUMED_IN_DOCUMENT`, so never offered as a confirmable answer). Every other question, and the specific "ground investigation completed" example from the brief, was evaluated and deliberately **not** mapped — see the task report for the full per-question reasoning (most notably `base`, which asks about the visible current surface via an enum, while the only related evidence describes sub-surface trial-pit strata in incompatible freeform prose).

**Source-priority gate** (`isProposableEvidence()`): only `CONFIRMED_BY_DOCUMENT` records with `confidence !== 'low'` are ever proposable — `ASSUMED_IN_DOCUMENT`, `PROVISIONAL`, `DOCUMENT_INTERNAL_INCONSISTENCY` and `CONFLICTING_EVIDENCE` are all excluded by construction, matching the brief's hierarchy exactly.

**Confidence/relevance fix (addressing the Batch 1B false positive):** a new, generic `DISCLAIMER_LANGUAGE` detector (`assessMatchConfidence()`) scores a match `'low'` confidence when it falls inside boilerplate/legal-disclaimer wording (e.g. "no warrantee is offered", "without written permission") — the exact real false-positive Batch 1B found (a "groundwater" match inside the real Job L PDF's disclaimer paragraph) is now scored `low` and excluded from ever being offered to Stage 1. Numeric matches with a real unit are scored `high`; everything else stays `medium`. This is a small, generic extension of the existing extraction pipeline, not a second confidence system.

**Confirm/Correct behaviour:** Confirm writes the Stage 1 answer via the identical `p.facts[key]` field a typed answer would use (never collapsed together with the evidence record) and separately records `p.stage1EvidenceAssist[key]` — `evidenceId`, `sourceFile`, `sourcePage`, `proposedValue`, `confirmedAt` — then follows the exact same navigation as a normal save (including the `rollerCount`/last-question special cases). Correct only hides the banner for the current render (session-local, not persisted) so the customer types into the same input and clicks the same existing "Save & continue" — `saveStage1()` records the divergence (`status:'CORRECTED'`, both `proposedValue` and `customerValue` retained) without altering `p.evidenceRecords` at all. The original evidence is never deleted after a correction.

**Provenance:** every evidence-assisted answer is fully traceable via `p.stage1EvidenceAssist[key]` — evidence record ID, source file, page/section, the original extracted value, and a confirmation/correction timestamp — kept entirely separate from `p.facts[key]` (the actual Stage 1 answer), so the two are never collapsed into one value.

**Backward compatibility:** `p.evidenceRecords`/`p.stage1EvidenceAssist` are read via safe defaults (`|| []` / `|| {}`) everywhere — an older project missing either field entirely simply behaves as `UNANSWERED` with no banner, i.e. exactly today's Stage 1, with no migration required.

**Internal review:** the existing internal/dev-only evidence ledger (`route('evidenceLedger', id)`) gained a new "Stage 1 evidence assistance" table — one row per existing Stage 1 question, showing customer answer, mapped evidence subject(s), evidence status, confidence, proposed answer, assist status, confirmation state and conflict state. Still gated the same way as before (not a customer-facing view) — see the still-open Batch 1B governance item on access-gating this route before production.

## Evidence Intelligence Batch 3 (2026-08-26) — IMPLEMENTED: Stage 2 evidence reasoning

**Scope:** turns the existing evidence ledger into structured, INTERNAL Stage 2 findings, surfacing only a deliberately restrained customer-facing summary. No Stage 2 question created/reworded/reordered/deleted; no Stage 3 action created; no Stage 3 solution/commercial remedy/supplier instruction ever exposed; the existing `runStage2Risks()`/`risks2`/`actions2` output is completely untouched.

**Where it lives:** appended to `evidence.js` (same file, no second evidence store) — `STAGE2_FINDING_STATUS`, `FINDING_RULES`, `deriveFindingStatus()`, `buildStage2Findings()`. Findings reference existing evidence records by `evidence_id` only. `app.js`'s `stage2Summary()` gained one new, clearly separate "Evidence-based observations" card (customer-facing summaries only — never `internal_detail`, evidence IDs, source files or `why_it_matters`), rendered only when at least one finding exists; a project with no evidence shows no change at all.

**Finding schema** (one object per `finding_id`, keyed by a **stable** key — `'f-' + rule.key` — so `created_at`/`resolved_at`/`resolution_evidence_ids` survive a ledger rebuild rather than being regenerated from scratch): `finding_id, project_id, category, subject, finding_status, severity_or_priority, customer_facing_summary, internal_detail, supporting_evidence_ids[], conflicting_evidence_ids[], source_files[], source_pages_or_sections[], confidence, why_it_matters, information_still_required[], stage3_candidate, created_at, resolved_at, resolution_evidence_ids[]`.

**Finding status** (`STAGE2_FINDING_STATUS`): the required 10 — `CONFIRMED_DOCUMENTARY_FINDING`, `POSSIBLE_ISSUE`, `NEEDS_REVIEW`, `INFORMATION_REQUIRED`, `ASSUMPTION_REQUIRES_CONFIRMATION`, `PROVISIONAL_SCOPE`, `EXCLUSION_RISK`, `CONFLICT_REQUIRES_CLARIFICATION`, `DOCUMENT_INCONSISTENCY`, `NO_ISSUE_IDENTIFIED_FROM_CURRENT_EVIDENCE`. `deriveFindingStatus()` never upgrades an assumption/provisional/exclusion/conflict into a confirmed conclusion — it correctly interprets the shared extractor's `ASSUMED_IN_DOCUMENT` status as either a genuine assumption or an exclusion, depending on which subject it actually is (`assumptionOverride`/`exclusionOverride` on each `FINDING_RULES` entry), and adds a `NO_ISSUE_IDENTIFIED_FROM_CURRENT_EVIDENCE` path for the 3 categories (contamination/asbestos/groundwater-flooding) where a document can genuinely report a clean result via a generic negation-language detector (`NEGATION_PATTERN` — matched the real Job L PDF's own "did not identify", "no asbestos was identified", "not within a designated flood zone" wording).

**Categories supported today:** ground_conditions, foundation_base_design, slab, contamination, asbestos, groundwater_flooding, gas_protection, drainage, underground_services, exclusions, quotations, structural_information, document_inconsistency — 13 of the ~19 named in the brief; the rest (planning, Building Control, fire, surveys, design dependencies, site levels) have **no evidence subject yet** and no finding is invented for them.

**De-duplication:** one finding per rule, referencing every matching evidence record by id — the same fact in two documents (e.g. 200 mm slab / A393 mesh) becomes one finding with multiple `supporting_evidence_ids`, never two findings.

**Conflict/resolution:** a cross-document `CONFLICTING_EVIDENCE` match always produces `CONFLICT_REQUIRES_CLARIFICATION`, never a chosen winner. If a later ledger rebuild shows the same finding key no longer conflicting, `resolved_at` and `resolution_evidence_ids` are set (once) while `created_at` is preserved — the finding's history is never discarded, per governance.

## Evidence Intelligence Batch 4 (2026-08-26) — IMPLEMENTED: Stage 3 action generation

**Scope:** turns eligible Stage 2 findings (`stage3_candidate: true`) into controlled, evidence-linked Stage 3 actions. **Party model** (`PARTY_TYPE`, all 13 required codes including `OTHER`): identified via generic role-phrase keyword scoring (`PARTY_TYPE_KEYWORDS`), never invented independently of an actual relationship mention. A "Name (Role)" pattern captures a real proper-noun name when present; otherwise `party_name` defaults to a generic, human-readable label derived from the type (e.g. "Structural Engineer") — never a fabricated company name. Parties are de-duplicated within a project via a stable `party_id` (type+name), and `source_evidence_ids[]` (the brief's own field name) holds every relationship id that mentions that party.

**Relationship schema:** exactly the fields specified — `relationship_id, project_id, relationship_type, package, scope, party_from, party_to, supporting_evidence_ids[], source_files[], source_pages_or_sections[], confidence, explicit_or_inferred, contractual_basis, exclusions_or_limits, interface_with[], created_at, superseded_by, notes`. Convention: `party_to` is always the acting party the relationship_type verb describes (who designed/supplied/installed/assisted/provided information/is responsible/is excluded); `party_from`, where present, is the second party the relationship is directed toward (e.g. the recipient of provided information/assistance).

**Explicit vs. inferred vs. unclear:** every relationship carries `explicit_or_inferred`. Direct-statement patterns (designs/supplies/installs/provides [reactions/data/etc.]/assists .../is responsible for/excluded from ... scope/client is responsible for or to provide ...) are `EXPLICIT`. One deliberately weaker rule — a "method statement discusses X" mention, directly matching the brief's own worked example — is `INFERRED`, always `INFORMATION_PROVIDED_BY`, always low confidence, and explicitly never `RESPONSIBLE_FOR`. `RESPONSIBILITY_UNCLEAR` is never produced by a text pattern — only by `crossCheckResponsibility()` detecting a genuine cross-document ownership conflict (see below).

**Critical rule — assistance ≠ responsibility (encoded structurally, not just documented):** `ASSISTED_BY`/`INFORMATION_PROVIDED_BY` are produced by entirely separate extraction rules from `RESPONSIBLE_FOR`/`DESIGNED_BY`/`SUPPLIED_BY`/`INSTALLED_BY` — there is no code path anywhere that reads an assistance/information relationship and promotes it into a responsibility one. `RESPONSIBLE_FOR` is only ever created from one exact direct-statement pattern (`RESPONSIBLE_FOR_PATTERN`) — never inferred from a party merely appearing in, authoring, drafting a method statement about, or assisting with a document (the Job C pattern: assisting with wider Building Control information does not mean accepting responsibility for it). A party merely NAMED in a multi-topic document with no matching explicit-relationship pattern produces **no relationship record at all** for that party in that document (the Job D/Job D site pattern: document possession/collation is not technical responsibility) — validated directly (scenario E below).

**Design/supply/install separation:** each is a separate `RELATIONSHIP_VERB_RULES` entry with its own verb pattern; a document naming three different parties for three different roles on the same subject produces three separate relationship records, never collapsed (validated: scenario F).

**Client responsibility:** `CLIENT_RESPONSIBILITY` is only ever created from its own dedicated explicit pattern (client/customer + "is responsible for"/"is/shall/will provide") — never as a generic "anything excluded elsewhere becomes the customer's problem" inference. `RESPONSIBLE_FOR`'s own pattern explicitly excludes a resolved-to-`CUSTOMER` party (that case is exclusively `CLIENT_RESPONSIBILITY`'s territory), avoiding a duplicate/overlapping relationship for the same statement.

**Contractual exclusions:** `EXCLUDED_FROM_SCOPE` records the excluding party (whose scope the item is excluded from), the excluded item as `scope`/`exclusions_or_limits`, and its package — and never automatically creates a `CLIENT_RESPONSIBILITY` relationship as a side effect (validated: scenario D — an exclusion alone never implies who becomes responsible unless a separate, independent statement says so).

**Interface intelligence:** `crossCheckResponsibility()` groups relationships by normalised scope text. Two different parties on the **same scope from the same document** (e.g. one document naming both the designer and the installer of one subject) is a genuine **interface** — `interface_with` is set on both, never collapsed into one relationship (validated: scenario A, F). A small, evidence-only `INTERFACE_PACKAGE_PAIRS` whitelist (`BUILDING_FRAME↔FOUNDATIONS_CIVILS`, `ENVELOPE↔FIRE`, `DOORS_OPENINGS↔FIRE`, `DOORS_OPENINGS↔ACCESS_SITE_LOGISTICS`) additionally cross-references relationships on genuinely different packages/parties — never hard-coded onto a project without two real underlying relationships to justify it.

**Responsibility conflict / precedence:** two different parties on the same scope via two genuine **ownership**-type relationships (`RESPONSIBLE_FOR`/`CLIENT_RESPONSIBILITY`/`SUPPLIED_BY`/`DESIGNED_BY`/`INSTALLED_BY`/`EXCLUDED_FROM_SCOPE`) from **different source documents** is a conflict — never silently resolved. Both original relationships are preserved completely untouched; a separate `RESPONSIBILITY_UNCLEAR` marker relationship is added, cross-referencing both via `conflicts_with` (mirrors `crossCheckEvidence()`'s own "flip status, keep both, cross-link" pattern for facts — no new philosophy). ## Guiding direction
The historical uploaded-project evidence reviewed this afternoon (see `MASTER-SPEC.md` § "Stage 2 evidence-first principle") demonstrated that Project Check can obtain materially useful pre-order information directly from client documents. The resulting direction:

**Project Check = evidence + discrepancy + action engine, not a longer questionnaire.**

The intelligence comes from cross-checking information across five broad layers, not from asking the customer more questions:

1. **Customer requirement** — what the customer says they need.
2. **Project evidence** — surveys, reports, drawings, investigations, photos, site data and documentary facts.
3. **Technical / supplier design** — what suppliers, engineers and consultants have actually designed or assumed.
4. **Commercial** — price, quotation status, scope, assumptions, exclusions, provisional amounts, dependencies and possible extras.
5. **Programme / delivery** — who needs to do what, when, and what depends on it.

## Document-level evidence model
A future governed evidence record should consider fields such as: project identifier; evidence/document identifier; document title; document class/type; provider/author; document date; issue date; revision; project/site; evidence status; source/provenance; project-match confidence; relevance; geographical/project coverage; limitations; duplicate relationship; revision/supersession relationship; alternative-option relationship; extracted facts; contradictions; findings; required actions; closure evidence. This is architecture, not a database schema — no production database is implemented as part of this document.

## Fact-level provenance
Every important extracted fact should eventually be traceable to its source, conceptually equivalent to: **Value | Unit | Source document | Source location/page | Document date | Revision | Status | Confidence | Conflict status | Supersedes/superseded-by.** Project Check must not design the future system so a new value silently erases old project history — a superseding fact should point back to what it superseded, not delete it.

## Evidence status
At minimum: `CURRENT`, `SUPERSEDED`, `HISTORICAL`, `DRAFT`, `PRELIMINARY`, `APPROVED`, `DUPLICATE`, `ALTERNATIVE OPTION`, `INCOMPLETE`, `UNMATCHED`. `UNMATCHED` means Project Check cannot safely assign the evidence to a project/asset from the information available — the system must not guess.

**Disambiguation (confirmed 2026-08-26, audited during the Evidence Meaning/Provenance/Maturity enhancement):** this is a **document-lifecycle** axis (is this document itself current, superseded, a duplicate, etc.) — it remains **architecture-only, not implemented**. It is a different concept from the `evidence_status` field `evidence.js` actually implements (`CONFIRMED_BY_DOCUMENT`/`ASSUMED_IN_DOCUMENT`/`PROVISIONAL`/`CONFLICTING_EVIDENCE`/`NOT_YET_KNOWN`/`DOCUMENT_INTERNAL_INCONSISTENCY` — a **fact-confirmation** axis: how well-established is this one extracted fact). The similar name is a documentation risk, not a code conflict; both are preserved, neither has been merged with or renamed into the other.

## Evidence processing status
`AVAILABLE` → `RELEVANT` → `COVERAGE CHECKED` → `LIMITATIONS IDENTIFIED` → `ACTION REQUIRED` / `NO ACTION REQUIRED`. A file existing in the project does not mean its subject has been resolved — "survey uploaded" is not equivalent to "survey sufficient."

## Duplicate / revision / alternative option
Project Check must eventually distinguish:
- **Duplicate** — the same underlying evidence uploaded more than once.
- **Revision** — a genuinely later issue that may supersede an earlier document.
- **Alternative option** — two current, genuine alternatives that must both remain visible (e.g. two supplier approaches under live consideration).

Genuine alternatives must never be discarded as duplicates, and superseded documents must never be deleted from project history — they remain visible under the "Evidence status" vocabulary above.

## Document integrity
A future intelligence layer should inspect professional-looking documents for: wrong customer; wrong project; wrong site; stale copied text; inconsistent dimensions; conflicting heights; conflicting dates; incorrect parties; revision conflicts; incompatible technical descriptions; outdated assumptions; incomplete approvals/signatures where relevant; internally contradictory statements. A professional-looking document must not automatically be trusted as internally consistent — a contradiction creates a finding requiring confirmation, and the system must not automatically decide which contradictory statement is correct.

## Cross-document discrepancy engine
Future evidence reasoning should compare facts between: customer requirements; project questionnaires; site evidence; surveys; planning information; supplier quotations; supplier drawings; structural calculations; civil/foundation design; drainage information; programmes; RAMS; revisions; handover information. Where important facts disagree, the system creates a controlled discrepancy for review — it must never silently pick whichever document is newest without assessing status/provenance.

## Requirement vs. design

## Real-world engineering dependency & revision intelligence (2026-08-27) — RECORDED FUTURE ARCHITECTURE, NOT YET IMPLEMENTED

Recorded from review of real-world engineering evidence involving supplier structural/support reactions, structural/foundation engineering, foundation drawings and revisions, civils information, civils quotations and related downstream project information (outside this repository — see "Status and authority" above; no source drawings, reaction schedules, reaction/load values or other source-project data from that review are reproduced anywhere in this document or in product code/fixtures). **Architecture/governance only — no schema, class, store or function for any of this is created by this record**, and none of Stage 1/2/3's existing behaviour changes because of it.

**Core engineering dependency principle.** Technical documents must not be treated merely as independent uploads — Project Check will eventually need to represent upstream/downstream evidence dependencies between them. A **representative** (not universal, not mandatory) dependency pattern:

`BUILDING STRUCTURAL DESIGN → SUPPLIER STRUCTURAL / SUPPORT REACTIONS → FOUNDATION ENGINEERING → FOUNDATION DRAWINGS / DETAILS → CIVILS PRICING / PROCUREMENT → CONSTRUCTION`

Different projects genuinely have different designers, suppliers, responsibilities, contractual interfaces, sequencing and procurement routes — this chain illustrates the KIND of dependency Project Check must eventually be able to represent, never an engineering rule every project must follow.

**Revision/change principle.** A material change to an upstream technical input may make dependent downstream information **potentially stale** — e.g. revised support reactions may put an existing foundation design in question. Project Check must NOT automatically conclude the existing downstream work is wrong, that redesign is definitely required, or that it is automatically invalid. Instead, future logic should identify: what changed; what evidence depended on the previous information; which downstream packages may be affected; what professional confirmation may now be required. **Materiality and actual dependency must govern reassessment** — never "any revision anywhere reopens everything downstream."

**Evidence/provenance principle — OBSERVED / INFERRED / CONFIRMED.** Chronology is useful evidence but does **not** prove an engineering dependency. A foundation drawing issued after a reaction schedule suggests (does not prove) the reaction information was available to the foundation designer. Project Check must preserve the distinction between a relationship that is merely **OBSERVED** (e.g. two documents coexist, similar dates/geometry), one that is **INFERRED** (a plausible but unconfirmed relationship, e.g. from chronology or subject-matter overlap), and one that is **CONFIRMED** (supported by drawing references, calculation references, design-basis documents, transmittals, revision records, correspondence, or professional confirmation). Inference must never be silently converted into fact — this extends the SAME discipline already governing this file's `evidence_status`/`OBSERVED`-style provenance concepts (see "Evidence status", "Fact-level provenance" above) to relationships BETWEEN documents, not just facts within one.

### Core intelligence principle — Project Check is not a file store
The discovery review's single most load-bearing conclusion: Project Check's differentiated value is not in storing uploaded documents, but in reliably understanding what a document *is*, what it *states*, what it *depends on*, what *responds to it*, and what about that picture remains *uncertain or absent*. Conceptually:

`SOURCE EVIDENCE → DOCUMENT IDENTITY → PROVENANCE / ORIGINATOR / STATUS → EXTRACTED FACTS → GEOMETRY / ZONES WHERE AVAILABLE → REQUIREMENTS → RELATIONSHIPS / DEPENDENCIES → CONFLICTS / GAPS / UNCERTAINTIES → CHANGE EVENTS → ACTIONS / CLOSURE → PROJECT SUPPORT`

Every important fact and relationship must retain provenance back to its source evidence — this is the same discipline already governing this document's "Fact-level provenance" and "Evidence status" above, extended explicitly to relationships between documents, not only facts within one.

### Two intelligence layers
**A. Within-document intelligence** — facts extractable once a document's identity is known: document identity/number/revision/status/date/originator; dimensions; levels; reactions; design basis; requirements; specification; scope; quotation inclusion/exclusion.
**B. Relationship intelligence** — REFERENCES; DEPENDS_ON; DERIVED_FROM; SUPERSEDES; POSSIBLE_MATCH; CONFLICTS_WITH; REVIEWED_BY; RESPONDS_TO; CLOSES; MAY_STALE; HANDOVER_TO; REQUIRES. Relationship intelligence is judged, from the real evidence reviewed, to be a **principal source of Project Check's differentiated value** — a bare fact is useful, but the relationship around it (what it depends on, what references it, what is missing, what responds to it) is what actually protects a customer or professional from a bad decision. No implementation schema is created for either layer here.

### Document identity certainty
First-class architecture. Conceptual levels: **EXACT MATCH**; **PROBABLE MATCH**; **POSSIBLE MATCH**; **NO MATCH**; **IDENTITY UNKNOWN**. ### Referenced-but-absent evidence
First-class architecture (extends DI-01 above). Conceptual states: **PRESENT**; **REFERENCED / PRESENT**; **REFERENCED / NOT PRESENT**; **UNKNOWN WHETHER PRODUCED**; **POSSIBLE MATCH IN PROJECT RECORD**; **SUPERSEDED**; **CURRENT APPLICABILITY UNKNOWN**; **REQUIRED FOR REVIEW**; **CLOSURE EVIDENCE NOT FOUND IN REVIEWED RECORD**. Governing principle: **absent from the Project Record does not mean never produced.** (Illustrative, generic example: a groundworks method statement instructs the reader to "refer to the services drawing" for a project, but no services drawing is present anywhere in the reviewed record — this does not prove no such drawing was ever produced, only that it is not currently available to Project Check.)

### Fact/provenance model (conceptual)
Minimum conceptual information around any one fact: SUBJECT; VALUE; UNIT; DISCIPLINE; SOURCE TERM; NORMALISED CONCEPT; EVIDENCE CERTAINTY; SOURCE DOCUMENT; SOURCE LOCATION/PAGE/DRAWING POSITION where possible; PROJECT; CURRENT APPLICABILITY. The UNIT field is not decorative: real discovery evidence showed the same underlying concept (a protected construction extent) expressed in one project as a linear distance and, in a different project, as a percentage of an elevation — without a UNIT field, these could be falsely treated as directly comparable, or falsely treated as conflicting, when in fact they are simply expressed in different units and cannot be compared without a conversion basis. No schema implementation.

### Spatially-scoped facts (now mandatory)
Not all building/site facts are project-global. Future intelligence must be able to scope a fact by PROJECT, BUILDING, ELEVATION, GRID, ZONE, OPENING, SUPPORT, FOUNDATION, DRAINAGE RUN, or other geometric/discipline location. Real discovery evidence directly demonstrated this is not a theoretical concern: a normal wall specification applied generally across a building, with a materially different, enhanced specification confined to one or two specific named walls or a stated percentage of specific elevations; ground conditions confined to one part of a site and not another; and support-specific structural reactions tied to individual named positions, not a single building-wide value. A single global value for wall specification, fire performance, ground condition, reaction, or level would have been **false** for every real project reviewed. No data schema is created.

### Civils Intelligence — conceptual architecture
Organised around: SITE/SURVEY; LEVELS; FOUNDATIONS/SUBSTRUCTURE; SLAB/FLOOR; DRAINAGE; EXTERNAL WORKS; ACCESS/PARKING; SERVICES/UTILITIES; GROUND/GEOTECHNICAL/CONTAMINATION; COMMERCIAL/SCOPE; DOCUMENT/REVISION/STATUS; DEPENDENCIES/INTERFACES; ACTION/CLOSURE. Governing safeguards, all evidence-derived: extract what evidence states, never independently judge engineering adequacy; keep existing/proposed/finished-floor/threshold/drainage levels conceptually distinct — never treat similar-looking level figures as equivalent without evidence; a ground-investigation recommendation existing is never the same as confirmed adoption into a foundation design; existing-condition evidence (e.g. a description of what is currently built) is never the same as original design evidence for that same element; a document referencing services/utilities information that is not itself present is a first-class "referenced-but-absent" evidence state, not a gap to silently fill; a revision letter alone is never the same as a known content change.

### Structural/Supplier Intelligence — conceptual architecture
Organised around: DOCUMENT/REVISION/STATUS; BUILDING GEOMETRY; GRID/SUPPORT POSITIONS; PRIMARY STRUCTURE; SECONDARY/STABILITY; REACTIONS; DESIGN BASIS/LOADS; BASEPLATES/HOLDING-DOWN; OPENINGS/LOCAL STRUCTURE; FOUNDATION INTERFACE; RESPONSIBILITY/SCOPE; DEPENDENCIES; ACTION/CLOSURE. The evidence-derived dependency chain: `SUPPLIER STRUCTURAL DESIGN → GRID/SUPPORT INFORMATION → REACTIONS → FOUNDATION DESIGN`. Critical safeguard, directly evidenced by real projects: **the existence of calculations, reactions, or foundation drawings never proves adequacy, currency, or that the latest upstream information was actually used** — a foundation designer's own record of having used supplier reactions proves the *dependency*, not the correctness, completeness, or currency of what was used.

### Building/Envelope/Fire Intelligence — conceptual architecture
Organised around: BOUNDARY RELATIONSHIP; ELEVATION; ZONE; ENVELOPE BUILD-UP; THERMAL PERFORMANCE; FIRE PERFORMANCE; STRUCTURAL FIRE PROTECTION; OPENINGS; PRODUCT/SYSTEM EVIDENCE; PRODUCT CERTIFICATION; PROJECT-SPECIFIC APPLICATION; PROFESSIONAL REVIEW; BUILDING CONTROL REVIEW; FIRE OFFICER REVIEW; QUOTATION/COMMERCIAL SCOPE; REVISION/CHANGE. The evidence-derived cross-discipline chain (**not solely a Planning issue, not solely a Building Regulations issue, not solely a Structural issue**):

`SITE / BOUNDARY GEOMETRY → FIRE / BUILDING REGULATIONS REQUIREMENT → AFFECTED ELEVATION / ZONE → ENVELOPE PERFORMANCE → SUPPORTING STRUCTURAL PROTECTION → SUPPLIER SPECIFICATION → QUOTATION / COMMERCIAL SCOPE → PROFESSIONAL / FIRE / BUILDING CONTROL REVIEW`

Five things are always kept distinct and never blurred: REQUIREMENT; SELECTED (real-project) SOLUTION; GENERIC ALTERNATIVE SOLUTION FAMILY; REVIEW STATUS; APPROVAL STATUS. **Fire-resistance requirements must never be reduced to a generic height-only lookup** — the applicable requirement must come from project-specific professional/regulatory evidence, considering use/purpose group, height, compartmentation, boundary conditions, structural function, fire strategy and other applicable regulatory conditions; Approved Document B (or equivalent) may provide regulatory context only, never a substitute for project-specific evidence.

**Zoned building specification (evidence-derived, architecturally significant).** A building cannot always be represented by one project-wide wall/envelope specification. Future architecture must support: `BUILDING → ELEVATION → ZONE/EXTENT → CONSTRUCTION BUILD-UP → PERFORMANCE → REASON/REQUIREMENT → SOURCE/REVISION`. A representative, generic pattern actually observed in real evidence: a normal envelope specification generally, plus a materially enhanced fire-resisting specification confined to a specific, named, boundary-driven zone, plus a structural-protection requirement for load-bearing elements within that same zone. This is recorded as a real, evidence-supported pattern, not a universal rule — no specific dimension, thickness, percentage, or fire-resistance period from any real project is recorded here.

**Product performance / project-application safeguard (first-class evidence-quality concept).** Real evidence showed generic manufacturer product-performance/certification documentation can describe one stated application/orientation, while a real project applies the same general product family in a different application — without this being evidence of an incorrect or non-compliant installation. The correct record is: **"product performance evidence found — applicability to the project-specific installation requires confirmation,"** never "the application was wrong" or "the system was non-compliant." Future intelligence may need to compare: `PRODUCT/SYSTEM → DECLARED PERFORMANCE → TESTED/CLASSIFIED ORIENTATION/APPLICATION → PROJECT-SPECIFIC USE → PROFESSIONAL/SYSTEM-DESIGNER CONFIRMATION`. Project Check must never decide technical applicability from document presence alone — this is a high-value future evidence check, not an automated engineering judgement.

**Fire-protection solution-family safeguard.** Project Check must not automatically prescribe any specific fire-protection family (e.g. mineral-wool/board lining, intumescent coating, sprayed protection, or any other) as a default answer to a fire-protection requirement. Conceptually: `REQUIREMENT/CONSTRAINT → POSSIBLE SOLUTION FAMILIES → PROJECT-SPECIFIC APPLICABILITY → COMMERCIAL/PROGRAMME/CONSTRUCTABILITY → PROFESSIONAL REVIEW → SELECTED SOLUTION → CLOSURE EVIDENCE`. Real, selected project solutions and generic technically-recognised alternative families must always be kept distinct and never retrospectively cross-prescribed between projects.

### Planning ↔ technical interface
Extends the existing Planning Intelligence architecture and preserves the existing authority-to-drawing-revision relationship principle (a planning/authority decision citing specific drawing numbers/revisions does not make every other drawing in the same folder approved). Future conceptual comparisons, only where a genuine second, independent technical evidence source exists for the same project: `PLANNING-AUTHORISED FOOTPRINT ↔ CURRENT SUPPLIER FOOTPRINT`; `PLANNING-AUTHORISED HEIGHT ↔ CURRENT SUPPLIER HEIGHT`; `PLANNING-AUTHORISED EXTERNAL FORM ↔ CURRENT DESIGN`; `PLANNING SITE/ACCESS ↔ CURRENT CIVILS`; `PLANNING REQUIREMENT/CONDITION ↔ CURRENT TECHNICAL ACTION`. Real discovery evidence showed plainly that many real projects will have **no second independent technical source to compare against** — this must be represented as an honest, expected, first-class outcome ("no independent second technical source exists"), not manufactured into a false comparison and not treated as a failure state.

### Conflict / gap / uncertainty concepts
Only categories with a real, evidence-derived basis are recorded as first-class: INTERFACE ASSUMPTION CONFLICT; GEOMETRY DIFFERENCE; REVISION UNCERTAINTY; CURRENT-APPLICABILITY UNCERTAINTY; MISSING REFERENCED EVIDENCE; STATUS/AUTHORITY DISTINCTION; PROFESSIONAL INPUT NOT CONFIRMED AS ADOPTED; PRODUCT PERFORMANCE/APPLICATION CONFIRMATION REQUIRED; QUOTATION SCOPE GAP; PROJECT-SPECIFIC DESIGN BASIS/CROSS-PROJECT CONTAMINATION RISK. Two important, evidence-tested distinctions: a **STATUS/AUTHORITY DISTINCTION** (e.g. a designer's own submission-status language versus an independent reviewing authority's own separate status vocabulary) is not the same thing as a **conflict** — different parties legitimately use different status vocabularies with different meanings; and two different, unrelated real projects using different project-specific design-basis values (e.g. different environmental/site design assumptions) is not a conflict either — it is a **PROJECT-SPECIFIC DESIGN BASIS / CROSS-PROJECT CONTAMINATION RISK**, where the real risk is one project's facts wrongly becoming another project's facts, not that the facts themselves disagree. Normal differences between unrelated projects must never be classified as conflicts.

### Revision / change intelligence (extends DI-02, DI-06)
Future intelligence must ask more than "did the revision letter change": WHAT CHANGED? WHICH FACTS CHANGED? WHAT DEPENDED ON THOSE FACTS? WHAT MAY NOW BE STALE? IS THE CHANGE MATERIAL? WHO NEEDS TO REVIEW? WHAT EVIDENCE WOULD CLOSE IT? Real evidence showed both possible outcomes: a revision pair where the specific compared figures were confirmed identical across the change (i.e. genuinely comparable content, no drift in that respect), and multiple other revision pairs where only the status/letter change was evidenced and the underlying content change could not be established at all. Both are legitimate, distinguishable states. Materiality assessment may require professional judgement; a change must never automatically invalidate every downstream item.

### Quote normalisation / supplier due-diligence (extends DI-03)
Governing future question: **does the supplier's price actually include the project requirements Project Check already knows about?** Potential conceptual scope states: INCLUDED; EXCLUDED; ASSUMED; CUSTOMER RESPONSIBILITY; BY OTHERS; PROVISIONAL; NOT ADDRESSED; UNKNOWN. A low headline price must never be treated as automatically like-for-like when a known technical/compliance requirement's inclusion in that price has not been confirmed. No quote comparison or supplier scoring is implemented by this record.

**Compliance/cost-optimisation principle.** Project Check's value is not only "find more required work/cost" — real evidence supports the pattern that correctly identifying a requirement's actual affected zone can also help **avoid unnecessary whole-building over-specification**: `ESTABLISH ACTUAL REQUIREMENT → ESTABLISH ACTUAL AFFECTED ZONE → CONSIDER APPROPRIATE COMPLIANT SOLUTION FAMILIES → OBTAIN PROFESSIONAL/AUTHORITY ACCEPTANCE`. Project Check must never prescribe a specific solution family as universally cheapest, and must never encode any material choice as automatically compliant.

### Building Control / responsibility / handover architecture
Current authoritative terminology (recorded here for accuracy, not as customer-facing wording): a **Local Authority/Local Council Building Control** route is distinct from a **Registered Building Control Approver (RBCA)** route — a private-sector *organisation* registered with the relevant national building safety regulator; this organisation-level registration is distinct from an **individual** building-control professional's own personal registration/qualification status. Future workflow architecture should distinguish, per requirement/comment: REQUIREMENT/COMMENT; ORIGINATING REVIEWER; AFFECTED DISCIPLINE; RESPONSIBLE PARTY IF EVIDENCED; SUPPLIER/CLIENT/PROFESSIONAL SCOPE; EVIDENCE REQUIRED; PROJECT CONSEQUENCE; CLOSURE STATUS; HANDOVER STATUS — **responsibility must never be guessed merely because a comment concerns a particular technical discipline.**

**Multiple, independent completion states (evidence-derived, must never be collapsed).** SUPPLIER SCOPE COMPLETE; BUILDING ERECTED; SUPPLIER COMMERCIAL ACCOUNT COMPLETE; BUILDING CONTROL PROCESS CLOSED; BUILDING READY FOR OCCUPATION; CLIENT-SIDE REQUIREMENTS COMPLETE. A real project can legitimately sit at different points across these dimensions simultaneously — a supplier's own contractual/commercial involvement may legitimately end before final client-side Building Control closure. Consistent with the existing evidence-status discipline above: **the absence of a final Building Control certificate in a historical supplier-side record does not prove Building Control never closed**, and an open Building Control comment does not by itself mean supplier failure or an incomplete project — closure evidence being absent from the currently reviewed record must always be worded as time-bound and evidence-set-scoped (e.g. "no closure evidence found in the reviewed record"), never restated as a standing, timeless claim (e.g. never "this was never closed").

### Project-specific knowledge isolation (hard principle)
**Project A fact must never become Project B fact.** Real evidence directly tested and confirmed this even where two unrelated real projects shared the same supplier, and in one instance the same named foundation-design professional — their project-specific dimensions, environmental/design-basis values, ground conditions, bearing assumptions, reactions, fire requirements, panel specifications, planning/approval status, and commercial figures remained genuinely different and were never treated as interchangeable. Same supplier ≠ same project value. Same client ≠ same project value. Same professional ≠ same project value. Same document family ≠ same project value.

**Evidence status:** `HISTORICAL` (see "Evidence status" above) — a completed, project-specific fire strategy for a different, already-built project. **Not** `CURRENT`/`APPROVED` guidance for a live Project Check customer project, and not a template to be reapplied automatically.

**Source / provenance:**

- Reviewed and recorded by: Stuart, 2026-08-26
- Section/page-level pinpoint references were not supplied when this record was written — only the document-level reference above is currently held. Add specific section/page citations alongside the facts below if/when they become available; do not infer or invent them.
- This record is **documentary/historical project evidence about a different, already-completed project** — it is evidence about how one specific fire strategy resolved one specific building's circumstances, not a Project Check rule, not customer-facing wording, and not validated against any current Project Check customer project.

### Extracted facts (project-specific, historical)

**Building:** 90 m × 35 m single-storey storage building, footprint 3,150 m², low occupancy.

**Means of escape:**
- The number of escape exits was driven by **travel distance**, not exit capacity — because occupancy was low. (Capacity-driven and travel-distance-driven exit counts are different calculations; this strategy used the latter for this specific low-occupancy case.)
- Six exits, distributed around the building perimeter.
- Exit locations provided escape in **at least two directions** from all points within the building.
- Maximum travel distance applied: **45 m**, for this normal-hazard storage use.
- Each escape exit specified at **minimum 750 mm** width — subject to other Building Regulations requirements potentially requiring a greater width for a given door.

**Escape door hardware (this strategy only):**
- Electromagnetic locks, linked to the fire detection/alarm system.
- Fail-safe: unlocked automatically on fire-alarm activation or power failure.
- Manual green break-glass override provided.
- **Non-generalisation flag:** this is how *this* strategy specified door fastening for *this* building's escape doors. Project Check must **not** create a universal rule that every escape door requires a push bar (or any other single fastening method). Door fastening requirements remain dependent on the applicable fire/escape strategy, occupancy/use, and other relevant circumstances of each project — this fact is recorded as an example of one valid approach, not as a Project Check rule.

**External escape routes / hardstanding:**
- Minimum 3.9 m wide at the narrowest point.
- Enabled occupants to distance themselves from the building by more than 1.8 m.
- **Non-generalisation flag:** do **not** convert this into a universal Project Check rule of 1.1 m / 1.5 m external walkway width (or any other fixed figure). That proposition is explicitly **UNRESOLVED** and remains unresolved until separately evidenced from other sources — this record neither confirms nor proposes it.

**Boundary / fire-spread (external fire spread to/from the relevant boundary):**
- Assessment determined the south elevation required fire protection because of the *combination* of its size and its proximity to the relevant boundary (a project-specific geometric/positional finding, not a fixed distance rule).
- The south wall was required to achieve **at least 60 minutes fire resistance for integrity and 15 minutes insulation**, or the stated alternative **REI 60** classification route.
- The approximately **2 m² exit-door opening** in that elevation was within the permissible unprotected area for that wall, and the strategy expressly concluded that **this exit door itself did not need to be a fire door**.
- This is the clearest illustration in this record of why "escape exit" and "fire-resisting door" are not the same thing — see terminology below.

### Terminology — must not be treated as interchangeable

Project Check must distinguish explicitly between:
- **Personnel/access door** — a door provided for normal day-to-day personnel access/egress. Its existence and location is a Stage 1 customer-supplied fact (`personnelDoors` in `app.js`/`stage1Questions`).
- **Escape exit** — a door (which may or may not be the same physical door as a personnel/access door) whose location, number, width and distribution are determined by a means-of-escape assessment: travel distance, occupancy, exit capacity, and directional-escape requirements. Not every personnel door is necessarily an escape exit, and not every escape exit is necessarily also a personnel door used for day-to-day access.
- **Fire-resisting door** — a door required to achieve a fire-resistance rating (e.g. integrity/insulation minutes, or an REI classification) because of its position relative to a boundary, its role in compartmentation, or another fire-spread reason. The Job B record above shows directly that a genuine escape exit can be correctly specified as **not** requiring fire-resisting construction, once the actual unprotected-area/boundary-distance assessment is done — the three concepts are independently determined, not a single interchangeable idea.

### Conflict flagged against existing Project Check logic — RESOLVED 2026-08-26: RETIRED FROM LIVE BEHAVIOUR

Project Check previously had a live, implemented, indicative calculation: **perimeter ÷ 32 m (rounded up)**, in `suggestedPersonnelDoorAllowance()` (`geometry.js`), surfaced to the customer as a Stage 1 hint banner on the personnel-doors question (`app.js` → `stage1()`) and reused as a warn-only Stage 2 geometry advisory (`validateGeometry()`, `geometry.js`). This Job B record demonstrated a real, professionally-produced fire strategy where the exit count was driven by **travel distance at low occupancy**, not by a perimeter/32-style capacity calculation — a materially different method that can produce a different answer. Following that flag, a separate, explicit correction task (2026-08-26, see `MASTER-SPEC.md` § "Personnel doors / means-of-escape responsibility split") **retired both live call sites**: the Stage 1 hint banner was removed entirely (the personnel-doors question now records the customer's requested quantity with no suggested/calculated value offered), and the Stage 2 `validateGeometry()` warning derived solely from this formula was removed. `suggestedPersonnelDoorAllowance()` itself is preserved unaltered and uncalled in `geometry.js`, purely as historical provenance — not deleted, per instruction. ### Developing Project Check logic (architecture direction only — not implemented)
