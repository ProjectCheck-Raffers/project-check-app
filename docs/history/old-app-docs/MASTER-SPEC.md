## Stage 2 objective — pre-order readiness ("no surprises")
Stage 2's primary purpose is to help the customer reach the point of placing a building order with as few avoidable surprises as possible. It is not a standalone technical-consultancy exercise. Every Stage 2 question, evidence check, risk rule and piece of advice should be tested against:

> Could this issue create an unexpected cost, delay, specification change, design issue, civils issue, approval issue or installation problem when the customer is ready to order the building?

Relevant issue categories: building specification, price, foundations/civils, drainage/services, planning/Building Regulations/other approvals, site access, installation, programme, site readiness, or the customer's ability to proceed with the proposed building.

Where possible, don't just surface a risk — explain (in plain English) why it matters, what information is missing, what the customer should obtain or confirm, who may need to resolve it, and the sensible next action. Target customer outcome: *"I understand the important things that could affect my building before I commit to the order."*

## Stage 2 evidence-first principle
Where Project Check already has reliable information — uploaded documents, drawings, surveys, ground investigations, maps, photographs, existing project data or other credible evidence — it should use that rather than asking the customer to re-enter the same fact. Customer questions exist primarily to fill unresolved information gaps, not to re-collect what evidence already establishes.

Intended Stage 2 flow: customer information → evidence review → known facts extracted → unresolved information gaps → targeted customer questions → findings/advice → actions required before building order. Every customer-facing question must earn its place against the no-surprises / pre-order-readiness objective above — don't add a technical question just because technical information exists somewhere. **Do not ask the customer for information Project Check already has reliable evidence for.**

**Reinforced 2026-08-24:** newly uploaded project evidence (Job L site investigation information, associated site/aerial information, and other project/ground information supplied in the uploaded documents) was reviewed and confirmed this principle in practice — it demonstrated that Project Check can obtain materially useful pre-order information directly from client documents rather than relying entirely on questionnaire responses. This is a reinforcement of the flow above, not a second or conflicting rule. See "Stage 2 evidence-derived candidates" below for the specific subjects this review surfaced.

## Question, Evidence & Rule Development governance
No prior document under this name existed in the repo, sibling project folders, or the Architect MCP tool (which is a stateless LLM call with no document store) at the time this section was written — this is the first record of it, held here as part of MASTER-SPEC.md rather than as a separate file.

When reviewing or proposing a Stage 2 question, apply this three-part commercial test:
1. Could this issue cause a surprise, delay, cost change, design/specification problem or inability to proceed at building-order stage?
2. Can Project Check give useful advice, identify the evidence required, or recommend a sensible next action?
3. Does resolving the issue help move the customer closer to a viable building purchase?

If the answer is no to all three, the question probably doesn't belong in the main customer journey. This test sits alongside — it does not replace — existing question/data provenance discipline (see `geometry.js` / `geometry-audit.spec.js` for the audited provenance of geometry- and door-derived facts). It must never be used to casually delete or reword an existing locked question; where it conflicts with an existing question or rule, that conflict should be reported for a decision rather than silently resolved by rewriting the question.

Where appropriate, a Stage 2 finding should feed forward into Stage 3 (an action, support item, evidence request, decision, solution task or commercial-progression point — see "Combined Stage 2 / Stage 3 continuity rule" below) rather than being left as an isolated finding.

Stage 2 advice arising from this governance should, where appropriate, explain in plain English: what has been identified; why it matters; what remains unknown; what information/evidence is required; who normally needs to address it; what the sensible next action is; and whether it should be resolved before building order. Project Check remains an early identification and support product, not a substitute for the relevant competent professional.

## Stage 3 — commercial conversion objective
"Stage 3" here is the commercial-progression phase already represented later in the customer journey above (supplier-quotation comparison, requesting three quotations, the £99 Solutions and £249 support routes, and the continuing project workspace) — this section records its governing objective, not a new unbuilt phase.

**Traceability note:** this is the first authoritative repository recording of Stage 3 commercial governance located during the current audit — not the first Stage 3 governance decision. Existing Project Check governance under **PROJECT CHECK — Stage 3 Workflow Brain Development (1000)** (which governs Stage 3 reasoning, outputs, actions and genuine-support workflow ahead of implementation) remains applicable and should be reconciled with this specification if or when its source record is made available to the repository.

Stage 3's main commercial objective is converting a suitably qualified Project Check project into a building sale. It must not lose sight of that by becoming an isolated advisory/technical service. Support should help the customer progress by: reducing uncertainty, helping resolve outstanding project issues, explaining next steps, supporting decisions, coordinating information where appropriate, keeping the project moving, removing avoidable barriers to order, and helping the customer reach a position where a building can confidently be purchased. Stage 3 combines **commercial progression + genuine project support** — support must be useful and credible, but its purpose is helping the project progress toward a viable order.

**Stage 3 decision test** — apply to any Stage 3 reasoning, output, action, recommendation or support workflow:
1. Does this help resolve uncertainty or a project obstacle?
2. Does this help the customer make a decision?
3. Does this help the project become more order-ready?
4. Does this help maintain momentum toward a viable building purchase?
5. Is Project Check genuinely helping the customer rather than simply adding process?

If an activity doesn't meaningfully contribute to the customer's project journey or commercial progression, challenge whether it belongs in Stage 3.

## Combined Stage 2 / Stage 3 continuity rule
Stage 2 finds the things that could surprise the customer before they order; Stage 3 helps resolve those things and moves the qualified customer toward buying the building. A Stage 2-identified issue should, where appropriate, become a Stage 3 action, solution, support item or commercial-progression point — the customer should never feel Stage 2 produces a list of problems and then abandons them.

## Stage 1–4 continuity & real-world engineering dependency (2026-08-27) — RECORDED FUTURE ARCHITECTURE, NOT YET IMPLEMENTED

The detailed engineering-dependency/revision/evidence-provenance principles and the DI-01–DI-04 findings/future data-model concepts they inform are recorded in full in `EVIDENCE-INTELLIGENCE-SPEC.md` §§ "Real-world engineering dependency & revision intelligence", "Data Intelligence findings — DI-01 to DI-04", "Future data model concepts" and "Professional safeguards — evidence certainty" (2026-08-27) — this section records the customer-journey-level (Stage 1-4) framing only, to avoid duplicating that content here.

**The same issue/dependency travels through an evolving Project Record, not four unrelated reports:**

1. **Stage 1 — Anticipate** — *"What could matter and what will eventually be needed?"* Stage 1 should anticipate important project dependencies in customer language, without exposing engineering terminology, technical value tables, or representing preliminary information as verified engineering. It must never certify foundation (or any other) adequacy.
2. **Stage 2 — Investigate** — *"What evidence exists, what is missing, and does it agree?"* Stage 2 should establish evidence completeness, evidence consistency, and dependencies — document identity/family/number/revision/status/date/provenance, relevant extracted technical information, whether related evidence appears aligned or conflicts, and whether a dependency is OBSERVED, INFERRED or CONFIRMED (see `EVIDENCE-INTELLIGENCE-SPEC.md`). Stage 2 does not independently certify structural adequacy.
3. **Stage 3 — Resolve** — *"What needs to happen, who needs to act, and what evidence closes it?"* Where Stage 2 identifies an unresolved dependency, conflict or missing confirmation, Stage 3 should convert it into a controlled resolution path: issue, affected discipline/package, required action, appropriate responsible professional/interface, information to be exchanged, required outcome, evidence required for closure, and activities potentially affected while unresolved — consistent with this document's own existing "Stage 3 — commercial conversion objective" and `EVIDENCE-INTELLIGENCE-SPEC.md` § "Stage 3 action model".
4. **Stage 4 — Control / Project Support** — *"Has it been done, is it still valid, and has anything changed?"* Stage 4 is the future live-control continuation of the SAME Project Record already begun through Stages 1-3 — not a disconnected generic project-management system — continuing to receive new evidence, recognise superseding revisions, compare relevant extracted information, maintain evidence dependencies, identify material changes and potentially-affected/potentially-stale downstream records, flag project interfaces, track required responses/actions, record closure evidence, maintain revision history, and reopen a previously-resolved issue only where a material upstream change genuinely invalidates the basis on which it was closed. Stage 4 must not blindly reopen every downstream item whenever a document revision appears — materiality, dependency and evidence govern reassessment, exactly as for Stage 3. Note: an existing, already-implemented commercial concept partially overlapping this future direction is the **£249 One-project support** route (§ "Pricing" below — "continuing review of supplier/manufacturer drawings and civils/foundation drawings"); this record does not change that existing pricing/product or imply Stage 4 is already built — reconciling the two remains future work.

**Cross-discipline intelligence.** Project Check's long-term value is not simply extracting more text from uploaded documents — it is understanding relationships between project disciplines (planning ↕ building ↕ structural engineering ↕ civils ↕ drainage ↕ services ↕ Building Regulations ↕ fire/access ↕ specialist layouts ↕ commercial scope ↕ programme). A material change in one discipline may create a requirement to reassess another. Provenance, evidence status, professional boundaries, uncertainty and responsibility boundaries must always be preserved when making those connections — never collapsed into false certainty.

**Professional safeguards** (see `EVIDENCE-INTELLIGENCE-SPEC.md` § "Professional safeguards — evidence certainty" for the full statement): Project Check identifies, organises, compares and tracks technical evidence — it must never silently represent itself as having provided professional engineering verification where that requires an appropriately appointed professional, and must never infer structural adequacy merely from a drawing's existence, a later drawing's existence, the existence of calculations/reactions, sensible-looking chronology, or shared dimensions.

**Extension (2026-08-27) — supplier drawing intelligence.** Review of real-world supplier drawing packages (outside this repository; no real drawing data reproduced anywhere) confirmed that this SAME Stage 1-4/dependency architecture — not a separate one — must eventually treat drawings as more than extracted text: geometry, structural arrangement, openings, interfaces, drawing-package relationships and revision comparison all remain future, unimplemented capability. It hard-governs the distinction between **uploader** (who supplied the file), **originator** (who produced the information) and **document status/authority** (what standing that specific document/revision has) — authority is never inferred merely from who uploaded a file. The full drawing-identity/package/geometry/uploader-authority/Stage-1-4-drawing-progression principles, and two further Data Intelligence findings (DI-05 drawing intelligence & geometry extraction; DI-06 drawing revision impact), are recorded in `EVIDENCE-INTELLIGENCE-SPEC.md` § "Supplier drawing intelligence" and its extended § "Data Intelligence findings — DI-01 to DI-06" — recorded here only as a pointer, to avoid duplicating that content.

**Extension (2026-08-27) — civils, structural, building/fire & cross-discipline discovery programme.** A subsequent, structured discovery review (outside this repository; no real project/customer/supplier names, addresses, dimensions, drawing numbers, technical values or commercial figures reproduced anywhere in this document or in product code/fixtures) tested this SAME Stage 1-4/dependency architecture against real Civils, Structural/Supplier, and Building/Envelope/Fire evidence, and against real cross-discipline relationships between them (including Planning). ## Compliance language and product positioning (all stages)

## Account, customer contact & consent
- **Registration data:** the account/onboarding flow captures email address and mobile telephone number for a **new** account (`app.js` → `authModal()`). A **returning** customer signing in with an already-registered email is never asked to re-enter a mobile number or re-tick the Terms checkbox — those fields and checks apply only on first account creation, matched by e-mail lookup.
- **Sign-in vs. create-account clarity:** the combined form now states plainly that an existing email signs the customer in and a new one creates an account, rather than leaving that ambiguous. This remains one combined form, not two separate screens — no new authentication stack was introduced (see "Prototype limitations" below; production authentication remains a separate, later piece of work).
- **Terms acceptance, Privacy Policy access and optional marketing are three separate things (corrected 2026-08-25):** the account-creation form has exactly one required legal-acceptance control — a Terms & Conditions checkbox ("I agree to the Terms & Conditions.") — validated with "Please accept the Terms & Conditions to continue." if left unticked. The Privacy Policy is **not** a checkbox and is **not** something the customer "accepts" or "consents to" — it sits alongside as plain informational text ("See our Privacy Policy to understand how we use your information.") with a working link and no validation of any kind. Marketing remains a separate, **unticked-by-default, optional** checkbox that account creation never depends on. Service/project contact (account, assessment, submitted information, uploaded evidence, requested support, project progression) does not depend on the marketing checkbox at all.
- **Right to erasure:** recorded in the Privacy Policy (`app.js` → `privacyPage()`) as a customer right, explained in plain English, with an explicit note that automated deletion is **NOT YET IMPLEMENTED — REQUIRED PRE-LAUNCH** and that some information may lawfully need to be retained. No UI in this prototype claims to process a deletion it cannot actually perform.
- **Terms & Conditions and Privacy Policy:** both are reachable customer-facing pages (`app.js` → `termsPage()` / `privacyPage()`, routed via `render()`), each linked independently from the account-creation form (see above — the Terms link sits inside the required checkbox's label, the Privacy Policy link sits in its own unrelated informational line) and from a persistent site footer (`index.html`, outside `#app`, present on every screen) — not just the homepage. Both are explicitly marked **DRAFT — REQUIRES LEGAL REVIEW BEFORE PUBLIC PRODUCTION LAUNCH** in their own text; neither invents a company registration number, registered address, insurance position or warranty that has not been separately confirmed, and both preserve the "Compliance language and product positioning" rules below (identify/flag/check, not approve/certify/guarantee). Note: the approved Terms Draft 4 text itself still refers to a "Privacy Notice" by name in its own clauses (28.3/29.2/45.14) — that is the verbatim Draft 4 wording, reviewable separately under Terms governance, not a naming inconsistency in this specification.

## Customer activity reporting & owner notifications
Stuart wants visibility of customer engagement with an assessment even when it isn't completed (started / in progress / abandoned / returned / completed), and wants to know when a customer begins or meaningfully progresses an assessment.

**Current architecture cannot genuinely deliver this yet, and this specification does not pretend otherwise.** The prototype/review build stores everything (accounts, projects, `p.history` activity entries, `p.stage`/`stage1Complete`/`stage2Complete` progress) only in each customer's own browser `localStorage` (see "Prototype limitations"). There is no server-side database and no channel by which activity on a customer's own device could ever reach Stuart's PC or phone — that is an architectural gap, not a configuration gap, and no notification of any kind (email/SMS/in-app) has been added to fake otherwise.

- **Status:** activity/progress data model — `PROPOSED — DESIGN REQUIRED`. Potential fields: customer, email, mobile, project, assessment start, last activity, current Stage, current question/progress, completion state, abandoned/incomplete state, evidence-upload activity, follow-up/support status — apply data minimisation.
- **Status:** owner/admin notification events (new assessment started, meaningful progress, inactivity, return, completion) — `PROPOSED — DESIGN REQUIRED`, with explicit debounce/inactivity rules still to be defined so it doesn't become notification spam for every click.
- **Minimum production capability required later:** a genuine server-side store of account/project/activity events (replacing local-only `localStorage`), plus an outbound notification channel (email/SMS/push) to reach Stuart off the customer's device — both are unbuilt; no backend was introduced as a side effect of this instruction.

## Prototype limitations
The local MVP stores data in browser localStorage and only records uploaded file metadata. Production must move authentication, project data, file storage, report enforcement, payments and supplier workflow server-side. This includes all personal data captured at account creation (email, mobile number, Terms/Privacy acceptance record, marketing-consent flag) — today it lives only in that customer's own browser, not on a server Stuart or Project Check can query or be notified from; see "Customer activity reporting & owner notifications" above. A temporary external review link into this build is review infrastructure only, not a production/public data-collection deployment.
